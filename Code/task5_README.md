# Task 5 - AIS Fusion Explained

This document explains `Code/task5.py` in simple terms. It is meant to help us
understand what the code is doing, where the data comes from, and how it
validates Scenario C from the project brief.

## What Task 5 Is About

Task 5 adds **AIS** to the tracker.

AIS means **Automatic Identification System**. In the real world, cooperative
vessels broadcast AIS messages containing information such as position,
identity, speed, and heading. In this simulation, AIS is simplified: each AIS
message gives the target vessel position directly in the NED coordinate frame.

The important thing is that AIS does not arrive at every radar scan. It arrives
asynchronously, roughly once every 3 seconds. In Scenario C there is also an AIS
dropout between `60 s` and `90 s`, where no AIS target reports are available.

The tracker must show that:

- it can use AIS when AIS is available,
- it can continue tracking during the AIS dropout using radar and camera,
- it can accept AIS again when AIS reappears,
- tracking with AIS is more accurate than tracking without AIS during the AIS
  available periods.

## Where The Data Comes From

The code does not talk to real sensors. The data is already generated by the

```text
harbour_sim_output/scenario_C.json
```

That JSON file contains:

- ground truth target states,
- radar measurements,

- GNSS fixes for the ownship/fusion vessel,

`task5.py` loads this file using:

```python
data = load_simulation_output(args.scenario)
```

By default, `args.scenario` is `"C"`, so it loads Scenario C.

## Sensors In This Task

### Radar

The radar is located at the NED origin:

```text
[0, 0] m
```

Radar measurements are already present in the JSON file. Each radar measurement
contains:

- range: distance from radar to target,
- bearing: direction from radar to target.

The radar sees around itself, has longer range, and is the main sensor that
keeps the track alive during AIS dropout.

In the code, radar updates are prepared in `prepare_update()` when:

```python
meas.sensor_id == "radar"
```

The radar measurement model uses `cfm.get_h_and_H(...)`, where CFM means
Coordinate Frame Manager. It computes the expected range and bearing from the
current predicted target state.

### Camera

The stereo camera is also simulated. It is not at the radar origin. Its NED
position is stored in `coordinate_frame_manager.py` as:

```text
[-80, 120] m
```

The camera has a limited field of view and shorter range. That means the target
is visible to the camera only during part of the scenario. The camera
measurements are already saved in the Scenario C JSON file, just like radar
measurements.

In this Task 5 code, the camera update uses only the camera bearing. This is
similar to the Task 4 logic: the camera gives a very accurate direction to the
target, so it helps reduce position error when it is available.

In the code, camera updates are prepared in `prepare_update()` when:

```python
meas.sensor_id == "camera"
```

### AIS

AIS is different from radar and camera.

Radar and camera give measurements relative to a sensor position:

```text
range + bearing
```

AIS gives the target position directly in NED coordinates:

```text
target north/east position
```

But the EKF measurement model used in this project expects range and bearing.
So the code converts AIS NED position into an implied range and bearing relative
to the ownship/fusion vessel position.

To do that, it uses the GNSS fix closest in time to the AIS message.

The idea is:

```text
AIS target position - nearest GNSS ownship position
    -> relative north/east displacement
    -> range and bearing
```

This happens in:

```python
ais_z_R(...)
```

and in `prepare_update()` when:

```python
meas.sensor_id == "ais"
```

## What GNSS Is Doing Here

GNSS gives the position of the ownship/fusion vessel in NED coordinates. It is
not a target measurement. It is used as a reference point for AIS.

When an AIS message arrives, the code finds the nearest GNSS fix:

```python
nearest_gnss(...)
```

Then it updates the Coordinate Frame Manager:

```python
cfm.update_vessel_pos(fix)
```

After that, AIS can be treated as a range/bearing observation relative to that
GNSS position.

## What The EKF Does

EKF means **Extended Kalman Filter**.

The target state is:

```text
[north position, east position, north velocity, east velocity]
```

At every measurement time, the EKF does two steps:

1. **Predict**
   The tracker predicts where the target should be at the new timestamp using a
   constant velocity motion model.

2. **Update**
   The tracker compares the real measurement to the predicted measurement. If
   the measurement is plausible, the tracker corrects the target state.

In the code, prediction happens here:

```python
F, Q = build_motion_model(dt, sigma_a)
tracker.x, tracker.P = tracker.predict(tracker.x, tracker.P, F, Q)
```

The actual update math is in:

```python
apply_update(...)
```

## What NIS Means

NIS means **Normalized Innovation Squared**.

It is a consistency check. In simple terms:

```text
How surprising is this measurement compared to what the tracker predicted?
```

If NIS is too high, the measurement is probably a false alarm or does not match
the current track. The code rejects updates with too high NIS using a chi-square
gate:

```python
ok = update["nis"] <= CHI2_99[update["dof"]]
```

The final report also prints how many accepted measurements are inside the 95%
NIS bound. This tells us whether the filter is reasonably consistent.

## What `task5.py` Runs

The script runs three versions of the tracker:

1. `without_ais`
   Radar + camera only.

2. `with_ais`
   Radar + camera + AIS.

3. `ais_only`
   AIS-only track. This proves that a target visible only in AIS can be
   initiated from AIS measurements alone.

This happens in:

```python
run_all(data)
```

Each version uses the same basic EKF logic, but with different allowed sensors.

## How Scenario C Is Validated

The output JSON contains:

```text
scenario_C_validation
```

This block checks the Scenario C success criteria directly.

### 1. Track Survives Dropout

During `60-90 s`, AIS is unavailable.

The tracker passes this check if:

- AIS updates during dropout = `0`,
- radar/camera updates during dropout > `0`,
- the tracker still produces a track through that period.

### 2. AIS Improves RMSE When Available

AIS should improve tracking accuracy when it is available.

The code compares RMSE in the AIS available windows:

```text
20-60 s and 90-150 s
```

In the current output:

```text
without AIS: 4.11 m
with AIS:    3.10 m
```

So AIS improves the result.

### 3. Smooth Reacquisition

AIS dropout ends at `90 s`.

AIS normally arrives every 3 seconds, so the tracker should accept AIS again at
about `93 s`.

The current result is:

```text
first AIS reacquisition after 90 s: 93.0 s
```

That passes.
