# Multi-Sensor Tracking Code Guide

This README explains how the code in this folder fits together. It is meant as
a practical guide for the project code: what each file does, where the data
comes from, how the tracker works, and how the outputs should be interpreted.

The separate Task 7 README is kept unchanged in `task7_README.md`. This file
only includes a Task 7 summary so the whole code folder has one combined
overview.

## Quick Start


## Data Source

The code does not read live sensor data. All scenarios are already simulated and
saved as JSON files in:

```text
harbour_sim_output/
```

Each scenario file contains:

- ground truth target states,
- radar measurements,
- camera measurements,
- AIS reports,
- GNSS ownship positions,
- sensor noise settings and scenario configuration.

The loader in `load_simulation_data.py` converts a scenario JSON file into a
`SimulationOutput` object. The task scripts then use this object instead of
reading JSON directly.

Example:

```python
data = load_simulation_output("C")
```

This loads:

```text
harbour_sim_output/scenario_C.json
```

## Coordinate System and State

The project uses an NED-style coordinate frame:

```text
N = north position [m]
E = east position [m]
```

Most trackers estimate a 4D constant-velocity target state:

```text
x = [N, E, vN, vE]^T
```

where:

- `N`, `E` are target position,
- `vN`, `vE` are target velocity components.

The motion model assumes that the target keeps roughly the same velocity between
updates:

```text
position_new = position_old + dt * velocity
velocity_new = velocity_old
```

Process noise is added so the tracker can still follow small changes in target
motion.

## Sensors

| Sensor | Measurement type | Role in the project |
|---|---|---|
| Radar | Range and bearing | Main baseline sensor. Used in all tracking tasks. |
| Camera | Camera measurement from a different NED position | Adds another viewing angle. Some task code uses bearing-only camera updates; later code can use range and bearing. |
| AIS | Target NED position reports | Cooperative target reports. AIS arrives less often and is processed asynchronously. |
| GNSS | Ownship/fusion-vessel NED position | Not a target sensor. Used as the reference position when converting AIS into range/bearing form. |

### Radar

Radar measurements are already stored in the scenario JSON files. Each radar
measurement contains:

```text
range_m
bearing_rad
```

The EKF predicts what the radar should see from the current state estimate, then
compares the prediction with the real radar measurement.

### Camera

The camera is located at a different NED position from the radar. This is
important because it observes the target from another angle. In Task 4 and Task
5, the camera is mainly used as an additional angular measurement, which helps
reduce position uncertainty when the target is visible to the camera.

### AIS and GNSS

AIS gives the target position directly in NED coordinates:

```text
target north/east position
```

The EKF measurement functions in this project are mostly written in
range/bearing form. Therefore, AIS is converted using the nearest GNSS ownship
fix:

```text
AIS target position - GNSS ownship position
    -> relative north/east displacement
    -> range and bearing
```

This lets AIS be used inside the same EKF update structure as radar and camera.

## EKF Logic

EKF means Extended Kalman Filter. It is used because range and bearing
measurements are nonlinear functions of Cartesian position.

Each update cycle has two main steps.

### 1. Prediction

The tracker predicts where the target should be at the next measurement time:

```text
x_pred = F x
P_pred = F P F^T + Q
```

where:

- `x` is the target state,
- `P` is the uncertainty covariance,
- `F` is the motion model,
- `Q` is process noise.

### 2. Measurement update

The tracker compares the real measurement with the predicted measurement:

```text
innovation = measurement - predicted_measurement
```

The update corrects the state and usually reduces uncertainty. Bearing
innovations are wrapped to avoid angle jumps around `pi` and `-pi`.

The update code uses the Joseph-form covariance update for better numerical
stability.

## Gating and NIS

NIS means Normalized Innovation Squared. It measures how surprising a
measurement is compared with the tracker prediction:

```text
NIS = innovation^T S^-1 innovation
```

where `S` is the innovation covariance.

NIS is used for two things:

- gating: reject measurements that are too unlikely,
- consistency checking: test whether accepted measurements behave statistically
  as expected.

For example, a 2D range/bearing measurement is checked against a chi-square
threshold with 2 degrees of freedom. A 1D bearing-only camera update uses 1
degree of freedom.

Small NIS is not automatically "best". The ideal result is that most accepted
updates stay inside the expected statistical bounds without being unrealistically
small or frequently too large.

## Task Files

### Task 3 - Radar-Only Tracking

File:

```text
Code/task3.py
```

Scenario A uses one target and radar-only tracking. The script starts from the
first true radar detection and runs a single EKF track.

The script checks:

- track confirmation using a 3-of-5 scan logic,
- steady-state position RMSE after confirmation,
- NIS consistency for radar updates.

The key idea is to prove that the basic radar EKF works before adding more
sensors.

Output figure:

```text
figures/task3/scenario_A.png
```

### Task 4 - Radar and Camera Fusion

File:

```text
Code/task4.py
```

Scenario B adds the camera to the radar tracker. It compares three approaches:

- radar-only baseline,
- sequential fusion,
- centralised fusion.

Sequential fusion means:

```text
predict -> radar update -> camera update
```

Centralised fusion means:

```text
predict -> one joint radar + camera update
```

The script reports RMSE values and generates plots for position error,
trajectory, and NIS.

Output figures:

```text
figures/task4/tracking_performance.png
figures/task4/trajectory_comparison.png
figures/task4/nis_comparison.png
```

Current note: the Task 4 fusion comparison uses the time interval where matching
radar-camera measurements are available. The radar-only line continues over the
full scenario, so compare the reported fusion values with that interval in
mind.

### Task 5 - AIS Fusion

File:

```text
Code/task5.py
```

Scenario C extends the radar-camera EKF with AIS. This is an asynchronous fusion
task because AIS does not arrive at every radar/camera scan. AIS reports arrive
roughly every 3 seconds and can disappear during a dropout window.

The script groups measurements by timestamp. At each timestamp it:

1. predicts the tracker to that time,
2. checks available radar, camera, and AIS measurements,
3. uses NIS gating,
4. applies accepted EKF updates,
5. stores history for plots and metrics.

The script runs three trackers:

- radar + camera,
- radar + camera + AIS,
- AIS only.

The AIS-only run demonstrates that a track can be initiated from AIS
measurements alone.

Scenario C also includes an AIS dropout window:

```text
60 s to 90 s
```

During this window, the tracker should continue with radar/camera updates. When
AIS returns, the tracker should accept AIS again smoothly.

Main outputs:

```text
outputs/task5/scenario_C_task5_report.json
outputs/task5/scenario_C_without_ais.csv
outputs/task5/scenario_C_with_ais.csv
outputs/task5/scenario_C_ais_only.csv
outputs/task5/plots/position_error.png
outputs/task5/plots/trajectory.png
outputs/task5/plots/nis.png
```

Typical validation result:


### Task 6 - Gating and Data Association

File:

```text
Code/task6.py
```

Scenario D introduces multi-target tracking. Instead of one target and one
track, the tracker now has to decide which measurement belongs to which track.

The main ideas are:

- chi-square gating removes unlikely track-measurement pairs,
- Global Nearest Neighbour association chooses the best one-to-one assignment,
- unassigned measurements can start tentative tracks,
- missed tracks can coast temporarily,
- tracks are deleted after too many consecutive misses.

Track lifecycle:

```text
tentative -> confirmed -> coasting -> deleted
```

Task 6 reports MOTP and Cardinality Error:

- MOTP measures localization accuracy of matched confirmed tracks,
- Cardinality Error measures whether the number of confirmed tracks matches the
  number of active true targets.

Main outputs:

```text
outputs/task6/scenario_D_task6_report.json
outputs/task6/plots/trajectory.png
outputs/task6/plots/motp.png
outputs/task6/plots/cardinality_error.png
outputs/task6/plots/nis.png
```

## Main Metrics

| Metric | Meaning | Good result |
|---|---|---|
| RMSE | Position error compared with ground truth. | Lower is better. |
| NIS | EKF consistency check for accepted updates. | Mostly inside the expected chi-square bounds. |
| MOTP | Mean localization error for matched confirmed tracks. | Lower is better. |
| Cardinality Error | Difference between confirmed track count and active true target count. | Lower is better. |
| ID switches | Number of times a track changes its matched true target identity. | Zero is ideal. |

## Typical Processing Flow

Most task scripts follow this pattern:

1. Load a scenario from `harbour_sim_output/`.
2. Extract the measurements needed for that task.
3. Initialize one or more tracks.
4. Predict each track to the current measurement time.
5. Convert the measurement into the EKF measurement model.
6. Compute innovation and NIS.
7. Gate or reject unlikely measurements.
8. Apply EKF updates for accepted measurements.
9. Update track state if track management is enabled.
10. Save metrics and plots for validation.

## Notes and Limitations

- The scripts use simulated data, not live sensors.
- Some earlier task files are more direct and script-like, while later tasks are
  more structured.
- Task 4 currently compares fusion over the interval where camera measurements
  are matched to radar measurements. Keep this in mind when comparing full
  radar-only RMSE against fusion RMSE.
- AIS is converted through GNSS ownship position before being used by the EKF.
- NIS plots should be interpreted by measurement dimension. A 1D measurement and
  a 2D measurement do not use the same chi-square threshold.
